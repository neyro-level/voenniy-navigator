# План: сервисное позиционирование, бриф главной и страница «О сервисе»

## Цель задачи

Привести документы проекта «Военный навигатор» к новой утверждённой рамке позиционирования:

- главный субъект сайта — **Военный навигатор** как сервис выбора новостройки и сопровождения покупки по военной ипотеке;
- Михаил Хряпин — **экспертное лицо, главный навигатор сервиса и ответственный за первичный разбор / логику отбора**;
- главная страница становится сервисным hub, а не личной страницей Михаила;
- появляется отдельная entity/trust-страница `/o-servise/` — «О Военном навигаторе»;
- `project-docs/PROJECT_STANDARD.md` больше не должен существовать как отдельный стандарт: его актуальные правила нужно перенести в `project-docs/PASSPORT_PROJECTS.md`, затем убрать из навигации и удалить.

- В коде главной много фактуры, которую можно частично вынести на страницу о сервисе: `src/pages/_home/05-Review.astro`, `07-Service.astro`, `08-Trust.astro`, `09-Reviews.astro`.
- Текущий H1-кандидат для новой главной согласован пользователем: `Сервис выбора новостройки по военной ипотеке под вашу задачу`.

**Гипотеза, утверждённая пользователем в чате:**

- Новая публичная формула: `Военный навигатор — сервис выбора новостройки и сопровождения покупки по военной ипотеке. Михаил Хряпин — экспертное лицо и главный навигатор сервиса.`
- Страница о сервисе должна объединить сервисный слой и роль Михаила, а не быть чисто личной страницей.

## Что можно менять

В режиме Code можно менять:

- документацию внутри `project-docs/`;
- page briefs внутри `project-docs/briefs/`;
- после отдельного согласования реализации — route/components/styles для новой главной и страницы `/o-servise/`;
- `WORKLOG.md` после завершения документального этапа.

## Что нельзя менять

- Не менять код в текущем документальном этапе, пока не будут утверждены брифы.
- Не менять `.env`, `.env.local`, секреты и публичные значения env.
- Не выдумывать факты о команде, кейсах, наградах, партнёрах, юридических гарантиях.
- Не обещать «гарантию сделки», «официальный статус», «лучшие условия», если это не подтверждено.
- Не превращать сайт в безликое агентство: Михаил должен остаться видимым лицом доверия.
- Не расширять позиционирование до «недвижимость вообще»: фокус — новостройки / квартиры и покупка по военной ипотеке.

## Риски

- **Высокий:** если просто заменить «Михаил» на «мы», сайт станет безликим агентством. Нужно сохранить Михаила как лицо доверия.
- **Средний:** термин «недвижимость» слишком широк; лучше использовать «новостройка / квартира / покупка по военной ипотеке».
- **Средний:** удаление `PROJECT_STANDARD.md` без полного переноса правил создаст потерю стандартов тона и CTA.
- **Средний:** страница `/o-servise/` требует аккуратного разграничения: брендовый слой — Военный навигатор, экспертный слой — Михаил, юридический слой — ИП Мазур.
- **Средний:** статистика и отзывы должны быть подтверждены, иначе их нельзя расширять или усиливать.
- **Низкий:** добавление `/o-servise/` в Header может перегрузить меню; лучше сначала footer/route map.

## Открытые вопросы

Без ответа можно безопасно сделать документальный этап, если использовать осторожные формулировки.

1. Финальный URL: оставить `/o-servise/` или выбрать `/o-voennom-navigatore/`?
   - Рекомендуемое решение: `/o-servise/` — короче и шире для entity/trust страницы.
2. Можно ли подтверждённо писать про «команду»?
   - Рекомендуемое решение: пока писать осторожно: `сервис`, `маршрут`, `Михаил`, `дополнительные эксперты / sales-слой` только в документах, не разгонять публичный текст без фактов.
3. Можно ли использовать цифры `65`, `180`, `с 2016` в новой странице `/o-servise/`?
   - Рекомендуемое решение: использовать как уже присутствующие в коде, но пометить в brief как факты, требующие клиентского подтверждения перед усилением.
